## Cambios clave en backend
- PayrollControllerImpl guarda la entidad y añade la referencia al empleado únicamente cuando existe, evitando NullPointerException posteriores.
- PayrollServiceImpl reorganiza save/update alrededor de syncAssociations, reutilizando los repositorios para enlazar automáticamente Employee y ExpenseUser cada vez que llega un payload con IDs.

- Las entidades Payroll y Expense ahora serializan sólo los IDs relacionados (employeeId, expenseUserId) mediante JsonGetter/Setter, lo que simplifica la capa REST y los clientes.

**Ejemplo ExpenseUserDto (solo IDs):**
```json

	"expenseUserDto": {
		"id": 1,
		"name": "Ada",
		"roleIds": [1, 2]
	},
	"concept": "Taxi aeropuerto",
	"amount": 120.50
}
```

**Ejemplo ExpenseDto:**
```json

	"id": 501,

	"expenseDate": "2025-12-01T09:00:00",
	"amount": 120.50,
	"expenseUserDto": {
		"id": 1,

	}

```

**Ejemplo PayrollDto:**
```json
{
	"id": 101,
	"amount": 2000.00,
	"payrollDate": "2025-12-01T00:00:00",
	"employeeDto": {
		"id": 1,
		"name": "Ada",
		"positionId": 1
	},
	"expenseUserDto": {
		"id": 1,
		"name": "Ada",
		"roleIds": [1, 2]
	}
}
```

**Notas técnicas:**
- El campo `roleIds` es ahora una lista de IDs (`List<Long>`) en vez de objetos embebidos.
- Todos los DTOs relacionados (ExpenseUserDto, ExpenseDto, PayrollDto, etc.) usan IDs para relaciones.
- Los mapeadores convierten entre entidades y DTOs usando solo IDs para roles y posiciones.
- La documentación y los ejemplos de API deben mostrar siempre los IDs, nunca objetos embebidos.

docs/researching/foreign-keys-vs-entities.md detalla el análisis sobre exponer IDs frente a entidades completas en los payloads y recoge la justificación técnica adoptada.
