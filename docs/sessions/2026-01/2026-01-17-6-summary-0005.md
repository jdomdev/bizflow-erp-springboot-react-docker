## 2. Corrección de Nombre de Rol en ExpenseController

### 2.1 Problema Detectado

Las notificaciones de gastos no se creaban porque el código buscaba usuarios con rol `"ROLE_ADMIN"`, pero en la base de datos los roles están almacenados como `"ADMIN"`, `"USER"`, `"MANAGER"` (sin prefijo `ROLE_`).

### 2.2 Diagnóstico

```sql
SELECT * FROM roles;
-- Resultado: ADMIN (id=1), USER (id=2), MANAGER (id=3)
-- NO existe "ROLE_ADMIN"
```

### 2.3 Solución Aplicada

**Archivo:** `backend/src/main/java/io/sunbit/app/controller/ExpenseControllerImpl.java`

```java
// ANTES (incorrecto):
notificationService.createForRole("ROLE_ADMIN", ...);

// DESPUÉS (correcto):
notificationService.createForRole("ADMIN", ...);
```

## 3. Implementación de Exclusión de Auto-Notificaciones

### 3.1 Problema

Cuando un admin creaba o editaba un gasto, se notificaba a sí mismo además de a otros admins. Esto generaba notificaciones innecesarias.

### 3.2 Nuevo Método en NotificationService

**Archivo:** `backend/src/main/java/io/sunbit/app/service/INotificationService.java`

```java
// Nuevo método añadido a la interfaz:
void createForRoleExcludingUser(String roleName, Long excludeUserId, 
    NotificationType type, String title, String message);
```

**Archivo:** `backend/src/main/java/io/sunbit/app/service/NotificationServiceImpl.java`

```java
@Override
public void createForRoleExcludingUser(String roleName, Long excludeUserId, 
        NotificationType type, String title, String message) {
    List<ExpenseUser> usersWithRole = userDao.findByRoles_Name(roleName);
    
    for (ExpenseUser user : usersWithRole) {
        // Excluir al usuario que realizó la acción
        if (excludeUserId != null && user.getId().equals(excludeUserId)) {
            continue;
        }
        create(user, type, title, message, null, null);
    }
}
```

### 3.3 Uso en ExpenseController

```java
// Al crear gasto - notificar a otros admins, excluyendo al creador:
Long creatorId = jwtTokenUtil.getUserIdFromToken(token);
notificationService.createForRoleExcludingUser(
    "ADMIN", 
    creatorId,
    NotificationType.EXPENSE_CREATED,
    "Nuevo gasto registrado",
    String.format("%s ha registrado un gasto de %.2f€: %s", 
        creatorName, expense.getAmount(), expense.getConcept())
);
```

## 5. Corrección de Permisos en Actualización de Gastos

### 5.1 Problema Original

Solo los administradores podían editar gastos, pero el propietario del gasto también debería poder editarlo.

### 5.2 Solución en ExpenseServiceImpl

**Archivo:** `backend/src/main/java/io/sunbit/app/service/ExpenseServiceImpl.java`

```java
@Override
public Expense update(Expense expense, String token) throws Exception {
    // ...
    boolean isAdmin = jwtTokenUtil.hasRole(token, "ADMIN");
    boolean isOwner = isRequestingOwnExpenses(existingOwnerId, token);
    
    // Permitir edición si es admin O si es el propietario
    if (!isAdmin && !isOwner) {
        throw new UnauthorizedException("No autorizado para editar este gasto");
    }
    
    // Si no viene expenseUser en el request, mantener el existente
    if (expense.getExpenseUser() == null && existingExpense.getExpenseUser() != null) {
        expense.setExpenseUser(existingExpense.getExpenseUser());
    }
    // ...
}
```

```java
    ExpenseUser user = userDao.findById(userId).orElse(null);
    if (user != null) {
        create(user, type, title, message, null, null);
    }
}
```

### 7.2 Problema con Employee ID vs User ID

**Descubrimiento importante:** El `employee_id` en la tabla `payroll` NO corresponde directamente al `user_id` en `expense_user`.

```sql
SELECT id, email, employee_id FROM expense_user WHERE employee_id = 13;
-- Resultado: user_id=9 (Dennis Ritchie) tiene employee_id=13

SELECT id, email, employee_id FROM expense_user WHERE id = 13;
-- Resultado: user_id=13 (Isaac Newton) tiene employee_id=17
```

### 7.3 Solución: Obtener IDs Antes de Guardar

El problema era que después de `payrollService.save()`, el objeto `employee` era un proxy no inicializado. La solución fue capturar los IDs **antes** de guardar:

**Archivo:** `backend/src/main/java/io/sunbit/app/controller/PayrollControllerImpl.java`

```java
@PostMapping("/")
public ResponseEntity<?> savePayroll(@RequestBody @Valid Payroll payroll) {
    try {
        // Capturar IDs ANTES de guardar (el proxy puede no estar inicializado después)
        Long employeeId = payroll.getEmployeeId();
        Long expenseUserId = payroll.getExpenseUserId();
        
        Payroll savedPayroll = payrollService.save(payroll);
        
        // Buscar usuario para notificar
        ExpenseUser targetUser = null;
        if (employeeId != null) {
            targetUser = userDao.findByEmployee_Id(employeeId).orElse(null);
        }
        if (targetUser == null && expenseUserId != null) {
            targetUser = userDao.findById(expenseUserId).orElse(null);
        }
        
        if (targetUser != null) {
            String monthName = savedPayroll.getPayrollDate()
                .getMonth().getDisplayName(TextStyle.FULL, new Locale("es", "ES"));
            
            notificationService.createForUser(
                targetUser.getId(),
                NotificationType.PAYROLL_AVAILABLE,
                "Nómina disponible",
                String.format("Tu nómina de %s está disponible. Importe: %.2f€", 
                    monthName, savedPayroll.getAmount())
            );
        }
        // ...
    }
}
```

## 8. Eliminación de Notificaciones Duplicadas

### 8.1 Problema

Al crear una nómina, se generaban 2 notificaciones idénticas porque existía código de notificación tanto en `PayrollControllerImpl` como en `PayrollServiceImpl`.

### 8.2 Diagnóstico

```sql
SELECT id, user_id, title, message FROM notifications ORDER BY id DESC LIMIT 3;
-- ID 8 y 9: Misma notificación duplicada para user_id 9
```

### 8.3 Solución

Se eliminó el código de notificación de `PayrollServiceImpl.save()`, dejando la lógica solo en el Controller:

**Archivo:** `backend/src/main/java/io/sunbit/app/service/PayrollServiceImpl.java`

```java
@Override
@Transactional
public Payroll save(Payroll payroll) throws Exception {
    try {
        syncAssociations(payroll);
        LocalDateTime parsedDate = DateUtil.formattingDate(payroll.getPayrollDate());
        payroll.setPayrollDate(parsedDate);
        Payroll savedPayroll = payrollDao.save(payroll);
        // Notification is handled in PayrollControllerImpl
        return savedPayroll;
    } catch (BadRequestException | ResourceNotFoundException e) {
        throw e;
    } catch (Exception e) {
        e.printStackTrace();
        throw new Exception(e.getMessage());
    }
}
```

También se eliminaron imports no usados:
- `import io.sunbit.app.entity.NotificationType;`
- `@Autowired private INotificationService notificationService;`

## 14. Notas Técnicas

### 14.1 Relación Employee-User

Es importante recordar que:
- `expense_user.id` ≠ `employee.id` en la mayoría de casos
- Un usuario (`expense_user`) puede tener un `employee_id` asociado
- Para notificar a un empleado: `userDao.findByEmployee_Id(employeeId)`
- Para notificar a un usuario directo: `userDao.findById(expenseUserId)`

### 14.2 Proxy de Hibernate

Después de `save()`, las entidades relacionadas pueden ser proxies no inicializados. La solución es:
1. Capturar los IDs **antes** de guardar
2. Usar los IDs capturados para buscar las entidades relacionadas después

### 14.3 Formato de Meses en Español

```java
import java.time.format.TextStyle;
import java.util.Locale;

String monthName = payrollDate.getMonth()
    .getDisplayName(TextStyle.FULL, new Locale("es", "ES"));
// Resultado: "enero", "febrero", etc.
```
