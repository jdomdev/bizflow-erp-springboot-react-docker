## 4. Fase 3: Compatibilidad de Hashes BCrypt

### 4.1 Problema Detectado

El login fallaba con HTTP 401 aunque el password era correcto. Investigación:

```sql
-- Hash en BD
$2b$10$ce8uq6ZraOfyEkCnCi3K9OKT5irf/UgIArEucKWdQ7u3gx0iF6Ek6
```

El prefijo `$2b$` es generado por Python bcrypt, pero Spring Boot espera `$2a$`.

### 4.2 Investigación Técnica

```python
# Python bcrypt genera $2b$
>>> bcrypt.hashpw(b"password", bcrypt.gensalt(10))
b'$2b$10$...'

# Spring Boot BCryptPasswordEncoder espera $2a$
// Java BCrypt
$2a$10$...
```

Aunque `$2b$` y `$2a$` son funcionalmente equivalentes, Spring Boot no los reconocía correctamente.

### 4.3 Solución Implementada

Se modificó `generate_password_hashes.py` para convertir el prefijo:

```python
def generate_hash(password: str) -> str:
    """Generate BCrypt hash for password.
    
    Note: Python bcrypt generates $2b$ prefix, but Spring Boot's
    BCryptPasswordEncoder expects $2a$. They are functionally equivalent,
    so we convert the prefix for compatibility.
    """
    hash_bytes = bcrypt.hashpw(password.encode(), bcrypt.gensalt(10))
    hash_str = hash_bytes.decode()
    # Convert $2b$ to $2a$ for Spring Boot compatibility
    if hash_str.startswith("$2b$"):
        hash_str = "$2a$" + hash_str[4:]
    return hash_str
```

### 4.4 Verificación

```bash
$ grep '\$2' sql/common/05_admin_bootstrap_dev_test.sql
    '$2a$10$2Ay/YaP1l9owIKCJv616X.9Mwo3G1Y864pO/LZs5IGjownNp/nJTa',
    '$2a$10$MOQJSzmcIi3XQs1T9eK0FOJ.8r.IsannVvLZhFZIHFHjchzfevPAm',
```

✅ Los hashes ahora usan `$2a$` y el login funciona correctamente.

### 5.1 Problema Detectado

```
WARNING - ⚠️ Users file not found: /secrets/users_with_passwords/dev_users.json
```

### 5.2 Análisis

El `seed_runner.py` calculaba la ruta así:

```python
SCRIPT_DIR = Path(__file__).parent          # /app
SECRETS_DIR = SCRIPT_DIR.parent / "secrets"  # /app/../secrets = /secrets
```

Pero el directorio `scripts/secrets/` no estaba montado en el contenedor.

### 5.3 Solución Implementada

Se añadió volumen en `docker-compose.yml`:

```yaml
x-api-seeder-common: &api-seeder-common
  build:
    context: ./scripts/seeds
    dockerfile: Dockerfile
  networks:
    - bizflow_erp_network
  restart: "no"
  volumes:
    - ./scripts/secrets:/secrets:ro  # ← NUEVO: Monta secrets como solo lectura
```

## 7. Fase 6: Vinculación Bidireccional User ↔ Employee

### 7.1 Problema Detectado

Ada y Alan se creaban via SQL bootstrap, lo que significaba que:
- No pasaban por `UserServiceImpl.save()`
- No se ejecutaba la lógica de vinculación
- `employee_id` quedaba NULL

```sql
-- Resultado antes de la corrección
SELECT email, employee_id FROM expense_user WHERE email LIKE '%lovelace%';
email                        | employee_id
-----------------------------+-------------
ada.lovelace@bizflowerp.com  | NULL        ← PROBLEMA
```

### 7.2 Análisis de la Lógica Existente

Ya existía vinculación User → Employee en `UserServiceImpl.save()`:

```java
// En UserServiceImpl.save()
Employee matchingEmployee = employeeService.findByEmail(user.getEmail());
if (matchingEmployee != null && user.getEmployee() == null) {
    user.setEmployee(matchingEmployee);  // User → Employee ✅
}
```

Pero NO existía la vinculación inversa Employee → User.

### 7.3 Solución Implementada

Se añadió la vinculación inversa en `EmployeeServiceImpl.save()`:

```java
@Override
@Transactional
public Employee save(Employee employee) throws Exception {
    try {
        syncPosition(employee);
        LocalDateTime parsedDate = DateUtil.formattingDate(employee.getBirthDate());
        employee.setBirthDate(parsedDate);
        
        // Save employee first to get the ID
        Employee savedEmployee = employeeDao.save(employee);
        
        // Vinculación automática inversa: Si existe un user con el mismo email, vincularlo
        if (savedEmployee.getEmail() != null) {
            Optional<ExpenseUser> matchingUser = userDao.findByEmail(savedEmployee.getEmail());
            if (matchingUser.isPresent()) {
                ExpenseUser user = matchingUser.get();
                if (user.getEmployee() == null) {
                    user.setEmployee(savedEmployee);
                    userDao.save(user);
                    log.info("Auto-linked employee {} with existing user {}", 
                        savedEmployee.getId(), user.getId());
                }
            }
        }
        
        return savedEmployee;
    } catch (BadRequestException | ResourceNotFoundException e) {
        throw e;
    }
}
```

También se añadió la misma lógica en `EmployeeServiceImpl.update()` para cuando cambia el email.

### 7.4 Nuevas Dependencias Añadidas

```java
@Autowired
@Lazy
IUserDao userDao;
```

Se usa `@Lazy` para evitar dependencias circulares.
