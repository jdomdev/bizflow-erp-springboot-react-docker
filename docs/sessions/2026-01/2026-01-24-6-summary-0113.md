## 3. Fase 2: Corrección del Esquema (Tabla Notifications)

### 3.1 Problema Identificado

El backend Spring Boot tenía una entidad `Notification` que intentaba crear/validar la tabla al iniciar, pero el schema SQL no la incluía.

### 3.2 Solución Implementada

Se añadió la tabla `notifications` a `sql/common/01_schema.sql`:

```sql
-- Notifications table
CREATE TABLE IF NOT EXISTS notifications (
    id BIGSERIAL PRIMARY KEY,
    employee_id BIGINT NOT NULL REFERENCES employees(id) ON DELETE CASCADE,
    title VARCHAR(255) NOT NULL,
    message TEXT NOT NULL,
    type VARCHAR(50) NOT NULL DEFAULT 'INFO',
    is_read BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    read_at TIMESTAMP,
    CONSTRAINT fk_notification_employee 
        FOREIGN KEY (employee_id) 
        REFERENCES employees(id) 
        ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_notifications_employee_id 
    ON notifications(employee_id);
CREATE INDEX IF NOT EXISTS idx_notifications_is_read 
    ON notifications(is_read);
```

### 3.3 Decisión de Diseño

**¿Por qué en `sql/common/` y no en un archivo específico de entorno?**

- La tabla `notifications` es estructural, no datos de seed
- Debe existir en TODOS los entornos (test, dev, prod)
- Forma parte del esquema base de la aplicación
- Consistencia: todas las tablas estructurales están en `01_schema.sql`

### 4.5 Decisiones de Diseño

- Permite auditoría separada de cambios en producción

- Resistente a ataques de fuerza bruta (cost factor 10)

### 6.1 Test de Re-ejecución

```
Payrolls: 300 created, 0 failed   ❌ DUPLICADO
Expenses: 120 created, 0 failed   ❌ DUPLICADO
```

**Los Payrolls y Expenses se duplicaban en cada ejecución** mientras que Employees y Users eran idempotentes.

### 6.3 Análisis de la Diferencia

**¿Por qué Employees/Users eran idempotentes?**

- El seeder hacía `GET /api/v1/employee` antes de POSTear
- Comparaba por email único
- Si existía, skip; si no, create

**¿Por qué Payrolls/Expenses no lo eran?**

- El seeder solo hacía POST directo
- No había verificación de existencia
- Cada ejecución creaba nuevos registros

### 6.4 Consulta al Usuario

**Decisión tomada**: Implementar idempotencia completa para TODAS las entidades.

## 7. Fase 6: Implementación de Idempotencia Completa

### 7.1 Estrategia de Idempotencia

```
┌────────────────────────────────────────────────────────┐
│  1. Pre-fetch: GET /api/v1/{entity}                    │
│     Obtener todos los registros existentes             │
└────────────────────────────────────────────────────────┘
                          ↓
┌────────────────────────────────────────────────────────┐
│  2. Build Key Set: Crear set de claves únicas          │
│     Payroll: (employeeId, payrollDate)                 │
│     Expense: (userId, date, amount, concept)           │
└────────────────────────────────────────────────────────┘
                          ↓
┌────────────────────────────────────────────────────────┐
│  3. For each item in JSON:                             │
│     IF key in existing_set → SKIP                      │
│     ELSE → POST to create                              │
└────────────────────────────────────────────────────────┘
```

### 7.2 Cambios en `seed_runner.py`

#### Nuevo método: `_fetch_existing_payrolls()`

```python
def _fetch_existing_payrolls(self) -> set:
    """Pre-fetch existing payrolls to build unique key set."""
    try:
        response = requests.get(
            f"{self.base_url}/payroll",
            headers=self.headers,
            timeout=30
        )
        if response.status_code == 200:
            payrolls = response.json()
            # Key: (employeeId, payrollDate as YYYY-MM-DD)
            return {
                (p['employeeId'], p['payrollDate'][:10])
                for p in payrolls
            }
    except Exception as e:
        self.logger.warning(f"Could not fetch existing payrolls: {e}")
    return set()
```

#### Nuevo método: `_fetch_existing_expenses()`

```python
def _fetch_existing_expenses(self) -> set:
    """Pre-fetch existing expenses to build unique key set."""
    try:
        response = requests.get(
            f"{self.base_url}/expense",
            headers=self.headers,
            timeout=30
        )
        if response.status_code == 200:
            expenses = response.json()
            # Key: (userId, date, amount, concept)
            return {
                (
                    e['expenseUserId'],
                    e['expenseDate'][:10],
                    str(e['amount']),
                    e['concept']
                )
                for e in expenses
            }
    except Exception as e:
        self.logger.warning(f"Could not fetch existing expenses: {e}")
    return set()
```

### 7.3 Decisión Crítica: Formato de Fecha en Payrolls

**Problema detectado**: Los JSON de payrolls tienen pagos quincenales (1 y 15 de cada mes).

**Formato inicial** (incorrecto):
```python
payroll_key = (payroll['employeeId'], payroll['payrollDate'][:7])  # YYYY-MM
```

Esto causaba que solo se registrara UN pago por mes, ignorando las quincenas.

**Formato corregido**:
```python
payroll_key = (payroll['employeeId'], payroll['payrollDate'][:10])  # YYYY-MM-DD
```

Ahora permite múltiples pagos por mes para el mismo empleado.

## 12. Decisiones Técnicas Clave

### 12.1 ¿Por qué Pre-fetch en lugar de Try/Catch en POST?

**Opción descartada**: Intentar POST y manejar error 409 (Conflict)

**Opción elegida**: Pre-fetch con GET y verificar antes de POST

**Razones**:
1. **Eficiencia**: Una sola llamada GET vs potencialmente cientos de 409s
2. **Claridad en logs**: "0 created, 1200 skipped" vs "0 created, 1200 failed"
3. **Backend intacto**: No requiere modificar los endpoints existentes
4. **Consistencia**: Mismo patrón que ya usaban Employees y Users

### 12.2 ¿Por qué 4 campos para Expense Key?

**Clave elegida**: `(userId, date, amount, concept)`

**Razonamiento**:
- Un usuario puede tener múltiples gastos el mismo día
- Pueden tener el mismo monto pero diferente concepto
- El concepto solo no es único (pueden haber "Taxi" duplicados)
- Los 4 campos juntos identifican unívocamente un gasto

### 12.3 ¿Por qué BCrypt con cost factor 10?

**Cost factor 10** es el default de Spring Security y ofrece:
- ~100ms para hashear una contraseña
- Resistente a ataques de fuerza bruta
- Balance entre seguridad y rendimiento
- Compatibilidad directa con `BCryptPasswordEncoder`
